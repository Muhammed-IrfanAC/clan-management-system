## Commands

```bash
npm run dev            # Next.js dev server (uses .env.local)
npm run dev:testing    # dev server against the testing DB (.env.testing)
npm run build          # production build (also typechecks — there is no separate typecheck script)
npm run lint           # eslint
npm run test           # vitest run (all *.test.ts)
npx vitest run src/lib/cwl/allocation.test.ts   # single test file
npx vitest run -t "name"                         # single test by name
npm run db:clone       # copy prod public schema+data into the testing project (scripts/clone-db.sh)
npm run db:grant       # (re)grant service_role, revoke anon, on the testing project (scripts/db-grant.sh)
```

Tests are Node-environment unit tests, mostly over the **pure** modules. I/O modules can be tested against `src/test/fakeSupabase.ts` — an in-memory supabase-js stand-in that enforces production's FK / ON DELETE rules (read from `pg_constraint`, which has drifted from the migration files) and supports per-statement fault injection — plus `src/test/fakeCoc.ts`, a scriptable CoC API; `sync.test.ts` shows the pattern, with `vi.useFakeTimers({ toFake: ['Date'] })` to move the clock across days. There is no DOM harness. Current suites cover `cwl/` (allocation, rotation, performance, history, lineup, rosterPost), `strikes/` (status, plan, dossier, mutations), `rules/` (warContext, automationScope), `kicks/` (watch, alertPost), and `warStats/` (attackClass, summary, load, statsPost, rankedWeek, weeklyPost). If you add a pure module, add a `*.test.ts` beside it.

## Architecture

ClanOps is a Clash of Clans clan-family management dashboard: Next.js 16 App Router + React 19, Supabase (PostgreSQL) for storage, and the official CoC API (via a proxy) for live game data. UI is vanilla CSS (`src/app/globals.css`) + Tailwind v4 + Lucide icons — no component library.

### Client state: Zustand stores + component split
Newer dashboard pages follow one convention — a per-feature Zustand store under `src/lib/stores/` is the single source of truth, and the page is split into small feature components under `src/components/<domain>/`:

- Stores: `strikeStore`, `memberDossierStore`, `settingsStore`, `membersStore`, `cwlStore`, `kickListStore`. State = server truth (fetched from API routes) + transient UI flags (per-action in-flight guards like `savingStrikeId`, `postingNote`; a shared `toast`).
- Mutations apply **granular, ID-keyed splices** of the changed row rather than a full refetch, so only the affected card re-renders (no whole-page flash). The API route returns the updated row; the store merges it.
- The `page.tsx` is a thin `'use client'` orchestrator (tabs, modals, mount-time load). Feature sub-components (e.g. `components/settings/RulesTab.tsx`, `components/members/dossier/MemberNotes.tsx`) call `useStore()` directly — they do **not** receive data via props.
- Pages on this pattern: `/dashboard/{strikes,members,members/[id],settings,cwl,kicks}`. `/dashboard/warnings` (sunset) still predates it.

### Auth & authorization (read this before touching any API route)
Identity and permission are deliberately separated across two DB columns — see `src/lib/auth-server.ts` and `src/lib/permissions.ts`:

- **Login is a tag plus a Discord code, no passwords** (`lib/auth/`). A player tag is public, so it only names who is logging in: `POST /api/auth/login` resolves the tag to its person and, if that person holds `access_role` and has a `discord_user_id`, DMs them a 6-digit code (`sendDirectMessage`, which the routing override never redirects — a code in the shared test channel would be handed to everyone there). `POST /api/auth/verify` exchanges the code for the signed JWT in the `clanops-auth` httpOnly cookie. `loginCode.ts` holds the pure rules — 5-minute single-use codes, 5 guesses each, at most 5 codes per person per 15 minutes with a 60s resend cooldown, which bounds both guessing and the DMs a stranger can trigger by typing a leader's tag — and `loginChallenge.ts` the DB half (`login_challenges`, migration 043; only an HMAC of the code is stored, keyed by `JWT_SECRET` and bound to the row id). Access is re-read when the code is redeemed, not trusted from when it was sent. A person with access but no linked Discord cannot log in until a leader links it. `jwtSecret()` fails closed when `JWT_SECRET` is unset; there is no fallback secret. `src/middleware.ts` guards `/dashboard/*` and gives a 30-day sliding session.
- **Identity** = `player_accounts.player_tag` (one global row per tag). **Permission** = `persons.access_role` (`super_admin` | `leader` | `co_leader` | NULL). Access lives on the **person**, so every linked alt inherits it and revoking it blocks all alts. `player_accounts.db_role` is a *clan-rank mirror only* (synced from in-game rank) and is **never** used for authorization.
- The JWT's role is a stale hint. Every mutation must re-check the **live** DB role: call `authorizeActive(request)` (returns `{ actorTag, role, personId } | { error }`) or `requireCapability(auth, cap)`. This closes the "revoked mid-session" gap. Never gate on the cookie's role alone. Once a route holds that live role, check further capabilities with `roleCan(auth.role, cap)` (no query) and authored content with `canModifyAuthored(auth, authorTag)` (author, any alt of the same person, or `content.override`); `hasCapability(tag, cap)` re-reads the role and is for when you have none. Read-only views use `authorizeActiveView(request, load)`, which verifies the cookie first and then runs the live role check alongside the view's queries, discarding the data if access was revoked. On the client, `fetchCurrentUser()` (`lib/currentUser.ts`) shares one `/api/auth/me` request across the layout, `useCurrentUser` and the stores.
- Authorization is a **capability model**, not scattered `if (role === ...)`. The pure `permissions.ts` defines the `Capability` union (`content.override`, `clan.create`, `account.delete`, `leader.manage`, `rules.delete`, `role.assign_any`, `role.assign_coleader`), the coded per-role defaults (`ROLE_CAPS`), and `can()` / `assignableRoles()` / `canAssignRole()`. Both API routes (the real enforcement boundary) and UI (button visibility) import the same pure `can()`.
- **Co-leader capabilities are runtime-configurable.** The `role_capabilities` table (migration 022) holds explicit per-`(role, capability)` overrides that win over `ROLE_CAPS`; only `co_leader` is editable, and only for the `CONFIGURABLE_CO_LEADER_CAPS` whitelist (excludes `role.assign_any`, keeping a single-owner model). `permissions-server.ts` loads overrides with a 15s cache; `/api/permissions` (super_admin only) toggles them and invalidates the cache. Always thread the loaded overrides into `can()` — the auth-server helpers do this for you.

### Data access
`src/lib/supabase.ts` exports a single **server-only** client built with the secret (service-role) key. The browser never talks to Supabase: every page loads through an API route — the screens' initial reads are bundled per page under `src/app/api/views/` (the independent queries run in parallel there) — and ESLint forbids importing `@/lib/supabase` from client code. The app does **not** rely on RLS for auth — every API route enforces auth in code via `auth-server.ts`. Routes use PostgREST embeds (e.g. `person:persons(access_role)`, `violations:strike_violations(*)`) heavily.

### Domain modules (`src/lib/`)
Business logic lives in `lib/`, kept free of React/JSX so sync jobs, API routes, and tests can all import it:

- **`sync.ts`** — reconciles each clan's roster against the CoC API. Accounts are resolved **globally by `player_tag`** (not per-clan) so players moving between family clans keep their person link, role, and access. **Sync never writes `person_id` or `added_at`**: new accounts are inserted with `ignoreDuplicates` and the roster upsert omits both columns, and a failed existing-account lookup aborts the sync. Before this, a lookup that failed unchecked made every member look new, and the upsert wrote `person_id = NULL` over whole rosters (the 2026-09-14 incident, which orphaned nearly every person). An empty roster for a clan with active members is also refused — a real clan cannot have zero members, so it is a bad read, not a mass departure. **Accounts are never auto-deleted** (migration 035): one gone from every family clan for longer than `inactive_cleanup_days` is marked `status = 'inactive'` — left off the members page, overview counts and the leader picker, shown greyed under "Inactive Accounts" in the dossier — because the row is what keeps a returning player's person link, strikes and kick-list entry attached; the roster upsert reactivates it. Each `syncClan` also returns its **arrivals** (members the clan did not have as active before the pass: new, back from `left`/`inactive`, or moved in from another family clan), which is what the kick list watches.
- **`cwl/`** — Clan War League. `allocation.ts` is the highest-risk piece: a **pure, deterministic, unit-tested** roster engine (no I/O) — feed it eligible accounts + clans + frozen constraints, get one allocation per **player account** (migration 026; a person's alts are each signed up independently, exactly as strikes are per-account). Clans are filled by an explicit **priority waterfall**: `cwl_season_clans.priority` orders them and each is filled to its full capacity (`warSize + maxBench`, lineup **and** bench) before anything spills to the next — so the flagship clan takes the strongest accounts and feeders absorb the spill. A bench slot is a wanted position, so `maxBench` is the leader's lever for how deep a clan may stack; the cost is that a low-priority clan can be left short of a lineup, which the roster board flags. Priority is rearranged via `PATCH /api/cwl/seasons/[id]/clans` and applied by `POST .../reallocate` (destructive regeneration, shared with season create through `generate.ts`). `leagues.ts` transcribes the official `/leaguetiers` table — 37 tiers, `id − 105000000` = a 0–36 ordinal — so eligibility gates on an exact **sub-division** ("Dragon 29+"), not just a major tier; `constraints.ts` folds pre-026 major-tier snapshots into that scale on read so frozen seasons keep their original meaning, and layers a per-clan override onto the season default **field by field** (a blank field inherits, matching what the override form promises). `live.ts` syncs live rounds; `rotation.ts` / `performance.ts` / `history.ts` derive suggestions and stats, and all three key **per account** for the same reason: CWL sign-up is per account throughout, so a person-level row describes nobody — `history.ts`'s cross-season career table merged a person's alts into one line carrying two alts' rounds, stars *and* misses, which mattered most in the miss columns, since a clean main averaged with a delinquent alt left neither legible and the repeat-misser list is read as a leadership signal. `personId` is still carried per row for linking back, and the season-trend "accounts fielded" count follows the same key (two alts occupy two war slots). The history page correspondingly stopped overwriting each war-member row's in-game name with the linked person's display name — harmless while rows merged by person, but with one row per account it printed the same name on every alt, leaving the tag as the only thing telling them apart. `lineup.ts` is the pure **planned-vs-actual** diff (allocations vs `cwl_war_members`): the in-game roster routinely differs from the formed one, and everything consequential already reads reality — performance, rotation fairness and the rule detectors all work off the war rows, so a swapped-in player who misses *is* struck and a planned player who never played is not. The diff exists so the drift is visible rather than silent; `lineupNotify.ts` is its DB/notify half, posting a round-reveal Discord notice (once per round, gated on `state = 'preparation'` and `cwl_rounds.lineup_notified_at`, stamped only on a successful send) and `LiveRoundsPanel` shows the same diff per round card — **on the same basis**, since the board had the identical stale-plan problem the notice did: it now compares against the clan's previous fielded lineup (walking back past unpolled rounds) and falls back to the plan only for a clan's first round, rewording to "unchanged" / "rotated in" / "resting this round" so the badge does not claim to be measuring a plan it is not. `lineupChange.ts` is the companion diff for a swap made **after** the reveal, and it exists because the plan-based one cannot see those: from sign-up onward `signupReconcile.ts` rewrites the board — bench flags included — from the in-game signup list, so the plan chases reality and a prep-day swap reads "as planned" one poll later. The comparison that still carries information is lineup-vs-lineup, so `live.ts` reads the stored lineup **before** overwriting it and `recordLineupChange` (in `lineupNotify.ts`) appends what changed to `cwl_rounds.lineup_changes` (migration 028's sibling, 030) and pings the swapped-in via `renderLineupSwap` (pure, `cwl/lineupPost.ts`, beside `renderRoundLineup`). Preparation only — the war roster locks at battle day. The event is written whether or not Discord accepts the message, and needs no idempotency stamp: the next poll compares against a lineup that already includes the change. `countSwappedPositions` is what the round card's collapsed badge counts, and it counts **players, not events**: `lineup_changes` records one entry per poll that noticed a difference, so three players swapped between two syncs collapsed to "1 swap" and expanded to three names — an event boundary is an artefact of polling frequency and means nothing to a leader. Which out pairs with which in is unknowable from a membership diff, so it counts positions changed (the larger side), deduped by tag across events with an out-then-back-in pair cancelling. The same poll **prunes** `cwl_war_members` rows for anyone no longer in the war — the upsert only added, so a swapped-out player kept their row, a 15v15 read back as 16 bodies, and once the round ended that ghost was a zero-attack member of an ended war, which is exactly what `war_missed_attack` strikes. `rosterPost.ts` is the pure renderer for the three **roster announcements** — per-clan roster, transfer call-to-action, leadership digest — and `rosterPostNotify.ts` its DB/send half: the clan rosters and the digest are **living messages**, posted once and then edited in place via `postOrEditDiscordMessage` (message ids in `cwl_season_clans.roster_message_id` / `cwl_seasons.digest_message_id`, migration 028), because a channel holding several contradicting roster posts is worse than none; the transfer call is the deliberate exception, sent fresh and pinging only the accounts that must move, auto-fired once per season (`cwl_seasons.transfer_call_posted_at`). It is split **one message per source clan**, into that clan's own channel — a member reads their own channel, and "you are in A, move to B" is a different instruction for every A; movers not in a family clan fall into a trailing family-wide group. No moves means **no message at all** (and no stamp, so the auto-call still fires if a later reallocation creates moves). Two format rules are load-bearing: the transfer call is **plain content with no embed**, because a mention inside an embed renders as a mention but never notifies — the message exists for the notification, so it cannot afford that; and the rosters carry **name + TH only**, laid out as aligned monospace columns inside code fences (league tier decides eligibility but printing it per line turned a 30-name list into a wall). Advancing a season to `transfers_pending` / `signed_up` announces automatically (`PATCH /api/cwl/seasons/[id]`, best-effort and swallowed); `GET/POST /api/cwl/seasons/[id]/post-roster` is the manual path, and its GET returns the *exact* payloads POST would send so `RosterPostModal` previews the real thing. `transferDetect.ts` is the pure half of **automatic transfer confirmation**: `player_accounts.clan_id` is rewritten on every roster sync, so a required move is already observable and the leader's checkbox stops being the only way the board learns of it. `detectCompletedTransfers()` (in `roster.ts`) runs as a step of `runFullSync` **after every clan is reconciled** — a move is only visible once the *destination* clan has been polled, so running it per clan would flip a mover depending on sync order. It moves transfer + allocation together in both directions (a player who moves back out re-opens the transfer), and two rules keep it from overruling a human: it skips any destination clan that isn't actively synced, and arrival requires `status = 'active'` as well as a matching `clan_id`, because the sync marks a departed row 'left' without clearing `clan_id`. Only `planning`/`transfers_pending`/`signed_up` seasons are touched — after that the in-game rosters are locked and later clan-hopping says nothing about whether the move was made in time. `signupReconcile.ts` is the pure half of **in-game signup reconciliation**: the league group's `clans[].members` is the authoritative list of who leadership actually signed into CWL (available from prep day, independent of round reveals), so from sign-up onward it **overwrites the plan** — recommendation included — and a signed-up account that was never rostered gets an allocation row of its own (only if a linked `player_account` exists; guests are logged, never invented). Bench is derived rather than assumed: who sits out is not in the signup list, so the planned flag stands until a round lineup is revealed, after which bench = signed up but not fielded — which is why the real bench can be **deeper than the season's `maxBench`**, and the game's number wins. `signupSync.ts` is its DB half, and also settles still-pending transfers (`done` if the account signed into its destination, else `missed`) because sign-up closing *is* the deadline. `live.ts` polls **every season except `completed`** — status is a leader's planning marker that lags reality, and gating on `signed_up` left a season sitting in `planning` with an empty live tracker all week — and moves the season to `in_progress` itself once a round is ingested (forward only). `coc-api.ts`'s `fetchFromCoCOptional` treats CWL 404s as the normal off-season empty state.

  Every poll first asks whether the member list it got back is **complete**: a CWL war is always exactly `teamSize` a side, so a shorter list is a partial read, not a lineup. That guard is load-bearing twice — a partial read would prune the missing rows (deleting real members, who then read as zero-attack bodies once the war ends, which is a `war_missed_attack` strike for a war they were in all along) and announce them as swapped out **with nobody swapped in**, which is what a leader saw on Discord and could not act on. The upsert still runs, because everything that *did* arrive is current; only the prune and the two notices are skipped, leaving the round unstamped so the next full read still announces it. Relatedly, the reveal notice no longer annotates a swapped-in account as "not on this clan's roster": `signupReconcile.ts` closes that gap on every sync, so the line was reporting a stale plan back to a player as though they were somewhere they should not be — about a lineup leadership had just set themselves. A bench call-up is still named, because that one is the roster working as designed.

  The reveal notice also **stops diffing against the plan after the first revealed round**, which is what made its swapped-out list run several times longer than its swapped-in list. `signupReconcile.ts` derives `is_bench` from "has appeared in *any* revealed lineup" — cumulative, so by round 3 nearly the whole signed-up roster is flagged a starter, and a 15-man war measured against 40 starters reports the entire rotating bench as swapped out while a returning player (already a starter by that rule) never registers as swapped in. Not a detection bug: a comparison that had outlived its input. So `notifyLineupIfRevealed` compares against the previous round's **fielded lineup** whenever one exists, falling back to the plan only for a clan's first round — symmetric by construction, since a CWL war is the same size every round and a body in means a body out. It walks backwards past any earlier round with no member rows rather than taking N−1 blindly, or an unpolled round would read as the whole war rotating in. `renderRoundLineup` takes a `basis` and rewords accordingly ("rotated in" / "resting this round"), because "swapped out" is an overstatement for a player the rotation rested, and the swap-in `reason` is forced to `unplanned` — "from the bench" is a claim about the plan, which is not what this comparison is against.

  **`rotation.ts` fairness has three tiers below rounds-played, and `isRoundSettled` is where its clock lives.** A round only counts as played, and only locks against further planning, once battle day has begun — the same line `performance.ts` draws, for the same reason: the lineup is published at the *start* of prep day, so a round in `preparation` has a roster but no war. Treating its existence as a decision made is what had the panel suggesting round 4 while round 3 was still on prep day, skipping past the one round a leader could still change. Beneath the rounds-played catch-up (still primary — it is the thing a benched player actually counts, and letting anything outrank it turns "fair rotation" into "best players play") the order now breaks ties on the family's **bonus-medal condition** (`BonusCondition`, default 4 rounds and 8★, printed in the panel header because it is a house rule the engine cannot verify and a wrong number is otherwise invisible), then on **performance**, then on strength. Chasing is gated on *reachability* — stars are capped at three per remaining round, and remaining rounds are the ones the account is actually available for, so a partial opt-out shortens its own runway — because prioritising a bonus already lost spends the war day twice over: once on a player who cannot reach it, once against the player who could. In the performance tiebreak a **missed attack outranks a better star rate**: a miss costs the clan a whole attack and is what the strike system acts on, so someone who showed up and two-starred beats someone who did not show up at all. An account with no attacks yet returns a neutral comparison rather than being ranked as though it had scored zero. `performanceByAccount` is the bridge, kept separate from `computeSeasonPerformance` because it also carries the rotation's own fields; both now key **per account**, since collapsing a player's alts would hand each account the other's stars when the rotation is filling two independent slots. The summary reports its shortfall against the **projected** season rather than today, since a gap the suggested plan already closes is not something to act on.

  `allocate()` takes **two exclusion sets**, both surfaced as `removed` rows carrying a reason rather than silently dropped — an unexplained absence from the board is what makes a leader regenerate the roster to find out why. The first is *ability*: `loadWarIneligibleAccountTags()` (in `roster.ts`) is every account holding a strike that is both inside the rolling 90-day window and `leadership_approved = false`, mirroring `isWarEligible` — per-account, so a struck alt never holds out its owner's main. The second is *willingness*: `cwl_season_optouts` (migration 031), a leader marking an account **not participating** this season. It is a separate table rather than a column on `cwl_allocations` for one reason — `generateAllocation` deletes and rebuilds every allocation row, so an opt-out stored there would silently undo itself the next time anyone reordered the clan priorities. Being an *input* to the engine makes it durable, and the freed slot is backfilled by the next-strongest account instead of leaving the clan short. Written through the existing `POST /api/cwl/allocations/move` as `opt_out` / `opt_in`, alongside the one-off `remove`; `opt_in` clears the flag but deliberately does **not** auto-place the account, since dropping a body back into a full clan would push it over its war size with nobody deciding who that displaces. Migration 032 adds a **round window** to that table, because the all-or-nothing version answered the rarer question: away for the first two war days, or gone after the fifth, is what a leader is usually told, and spending a full opt-out on either throws away five playable rounds. The window records the rounds the account *cannot* fight, and both ends being null is the whole season — so every pre-032 row keeps its meaning with no backfill. The distinction is load-bearing rather than cosmetic: a full opt-out is an **engine exclusion** (`loadOptedOutAccountTags` selects only the unbounded rows) and its slot is backfilled, while a partial one is **not excluded at all** — the account still has to be in a clan to fight the rounds it can, so it is rostered normally and the constraint is handed to `rotation.ts` instead. `availability.ts` is the pure shared semantics (`isFullSeason` is the switch every consumer branches on, rather than each re-deriving `!from && !to`; `untilRound`/`afterRound` throw on the empty windows "until round 1" and "after round 7", which describe an available player and would otherwise store a marker standing for no missed rounds). In the rotation, an unavailable account is removed from the round's candidates entirely rather than planned in and then benched — the latter spends a fairness slot on a round it was never going to fight and pushes someone who *could* have played onto the bench — and it surfaces as its own `unavailable` list per round plus an `unavailableRounds` count in the summary, since counting those as bench days would read as the rotation treating an absent player unfairly when it never had the choice. A lineup left short is named rather than quietly small. `RotationPanel` drops full-season opt-outs from the roster it hands the engine, rather than relying on the allocation exclusion alone — a row can still be on the clan because the leader marked the account *after* the roster was formed (`opt_out` does not delete the allocation) or because `signupReconcile.ts` put it back, and an account with no round to play contributed a zero row and a full column of Out to the one table whose job is "who sits next". An account that is both struck and opted out reports as struck — both exclude it, but only the strike is something a leader can act on. `signupReconcile.ts` can still put an opted-out account back on the board if the game says they signed up, which is the module's standing rule that reality outranks the plan; the board keeps showing the marker, so the contradiction is visible rather than resolved behind the leader's back.

  `rosterReason.ts` is the pure explainer behind the roster board's **exclusion callout** — why an account is not in a clan's fighting lineup. The engine already wrote its reasoning to `cwl_allocations.note` on every account it excluded, but that column was never selected into `cwlStore`, so the board showed a name in the Unassigned pile and no way to learn why short of re-reading the engine. Surfacing the note is most of it; `groupExclusions()` collapses shared reasons so the callout prints each once with its names rather than repeating a sentence per row, and falls back to a manual-removal reason for the leader's own `remove` (which has no engine reasoning behind it). **Bench** is the half the engine cannot annotate, because the honest answer changes with time: while the roster is being formed, bench follows from ranking past `warSize`, but from sign-up onward `signupReconcile.ts` overwrites the flag from the in-game lineup, which can sit the clan's third-strongest account. So `benchReason()` compares the account's position against the war size instead of assuming it follows — a strong benched account reads as somebody's decision, not the engine's arithmetic. Position is taken across the whole clan roster rather than within the bench list, or the comparison would be meaningless. A confident wrong reason is worse here than none, since it is what a leader would go and repeat to the player.

  **Clan scope (`components/cwl/useCwlScope.ts`).** A CWL season is a family-wide object, but almost nothing a leader *does* with it is: checking a lineup, chasing a missed attack, deciding who benches next round are each one clan's business, and rendering three clans' worth of rows meant scrolling past two of them every time. So `RosterBoard`, `TransfersPanel`, `RotationPanel`, `LiveRoundsPanel` and `PerformancePanel` scope to a single clan, with the family view one click away. It reuses the **dashboard header's existing clan switcher** (`ClanContext`, where `'all'` is the family) rather than adding a CWL-only control — a second selector would let the two disagree. Two panels stay family-wide by nature: the clan fill order (a priority only means anything relative to the other clans) and the unassigned pile (an account nobody rostered belongs to no clan). Scoping the performance table is just a narrower round set — a war member row belongs to one round and a round to one clan — which is why `computeSeasonPerformance` now treats its `rounds` argument as the **scope boundary** and skips member rows outside it; without that it would have summed every clan's stars under a heading claiming to be one clan's. The roll-up is keyed by **`player_tag`, one row per account** — it originally grouped by `person_id`, which merged a player's alts into a single row showing the sum of two independent wars (two alts fighting all seven rounds read as 14 rounds played, both star totals under one name). CWL sign-up is per account throughout — allocation, bench, strikes — so the person-level row described nobody; `personId` is still carried on each row for linking back.
- **`kicks/`** — the **kick list** (`/dashboard/kicks`): accounts leadership kicked, watched so a return to *any* family clan is noticed. The CoC API has no kick event (sync sees a kick exactly like a voluntary leave), so a kick is a leader's statement: "Mark as kicked" on a dossier account, add-by-tag (a never-synced tag gets an `inactive` account row created from the CoC API so the FK holds), or one click on the "left in the last 2 days" suggestions. `kicked_accounts` is keyed by tag with an FK to `player_accounts` (NO ACTION — `DELETE /api/players/[tag]` refuses a listed account, since deleting it would silently lift the ban). The watch covers the kicked account **and every other account linked to the same person**; anything linked to a person with `access_role` is never listed, suggested or alerted on (co-leaders kick their own alts to make room) — enforced on write and again on read. `watch.ts` is pure (tag normalisation, `matchKickedArrivals`, the page view, the departures filter); `alertPost.ts` is the pure Discord renderer; `kickList.ts` is the DB half behind `/api/kicks` (flat selects, so it runs on `fakeSupabase`); `arrivals.ts` is a fail-safe `runFullSync` step after every clan is reconciled that matches the pass's arrivals and posts to the **leadership** channel, pinging the Leadership role (`LEADERSHIP_ROLE_ID` in `lib/discordRoles.ts`) in plain content — never the player. No "already alerted" state is needed: each join is one arrival, and leaving then rejoining alerts again. Any dashboard user may add, comment on or remove entries.
- **`war.ts` / `warAttacks.ts`** — regular (non-CWL) war ingestion. `war.ts` polls each active clan's current war into `war_rounds`; `warAttacks.ts` persists per-attack detail (shared by regular wars → `war_attacks` and CWL → `cwl_war_attacks`) with `ON CONFLICT DO NOTHING`, which preserves the **first-sighting** `first_seen_at`/`first_seen_state` an attack was polled at — that immutable timestamp is what late-snipe timing relies on. Both are I/O modules.
- **`rules/`** — automated war-rule violation detection. The split mirrors cwl's pure/impure discipline: `warContext.ts` and `automationScope.ts` are **pure and unit-tested** (attack reconstruction + hit-up/late-snipe judgement; per-clan scope filter). `registry.ts` is UI-safe detector metadata (no server imports). The DB/orchestration half is `scan.ts` (runs enabled detectors, applies each clan's scope, commits) plus `detectors/` (`missedAttack`, `hitUp`, `lateSnipe` wrappers + `warContextLoad`). Built-in detectors: `war_missed_attack` (auto), `war_late_snipe` (auto), `war_unjustified_hitup` (review-mode → queues a suggestion instead of auto-striking). Leadership is exempt via `persons.access_role` (never in-game `db_role`). Per-clan `rule_automation_mode` (`always` | `cwl_only` | `never`, migration 018) gates which war types automate, enforced uniformly in `scan.ts`.
- **`strikes/`** — the discipline system that supersedes the legacy `warnings/` tables (warnings routes/UI still exist but are sunset). Same three-phase pure shape as allocation: `status.ts` derives active count / level / war-eligibility from a strike list (a strike is **active only within a rolling 90-day window** — expiry is *derived* from `issued_at`, there is no `expires_at` column, migration 020); `plan.ts` groups violations into stable one-strike-per-`(account, war)` containers; `dossier.ts` + `mutations.ts` build the leadership worklist and status transitions. `commit.ts` and `notify-context.ts` are the DB/notify half. Strikes are scoped **per account** (`player_account_tag`), not per person, so each alt is judged independently while staying linked for notifications/profile. Auto detectors commit strikes directly; `war_unjustified_hitup` queues to `strike_suggestions` and a leader confirms via `/api/rules/review/[id]`, which **folds** the violation into that war's existing strike (never a second strike). Trust-restoration is a checklist + a leader `leadership_approved` flag that clears the demotion intent but never removes the strike from the active count.
- **`cocTime.ts`** — pure normaliser for the CoC API's **compact** timestamps (`20260803T100000.000Z`, ISO 8601 *basic* format), which `new Date()` rejects outright. It hid for a long time because these values normally go straight into Postgres, which parses the basic format happily — so anything reading a war time back out of the DB is fine. It only breaks where an API value is used without that round trip, which is how the Discord lineup notices came to render `<t:NaN:f>` as their battle-day countdown. Applied at both ingestion boundaries (`war.ts`, `cwl/live.ts`) so nothing downstream needs to know; `discordTs` also degrades to the raw string rather than printing NaN.
- **`discord/`** — best-effort notifications posted by the bot (webhooks from migration 013 until 038 retired them). Infrastructure only, split by concern: `types.ts` (message shapes, client-safe), `format.ts` (pure helpers: `discordTs`, `truncateField`, `normalizeDiscordId`), `roles.ts` (role ids), `routing.ts` (purpose → destination, override config), `identity.ts` (person/account → Discord id), `transport.ts` (the **only** file that calls discord.com), and `index.ts`, the server-side entry point `@/lib/discord`. Message **renderers live with their domain** as pure functions returning a `DiscordMessage` — `strikes/strikePost.ts`, `warnings/warningPost.ts`, `cwl/lineupPost.ts`, `cwl/rosterPost.ts`, `kicks/alertPost.ts`, `unlinked/joinPost.ts` — and the caller hands the result to `sendDiscordMessage` with a resolved destination. ESLint enforces the boundary: a Discord API URL outside `transport.ts` in server code is an error, and components/pages/stores may import only `discord/types`, `/format` or `/roles`. **Bot routing** (migration 037; webhooks retired in 038): every routing step — purpose channel, `clans.discord_channel_id`, the family-wide fallback (`DISCORD_DEFAULT_CHANNEL_ID`) and the override — is a channel id, and `destinationForClan` resolves a `Destination` (`{channelId}`); a step with no channel id falls through to the next, and without `DISCORD_BOT_TOKEN` nothing is sent at all. A bot cannot rename itself per message, so under the override its messages carry a `-# 🧪 ClanOps · test routing` subtext line. A living message the retired webhooks posted cannot be edited by the bot (403), which the post-fresh fallback absorbs — the old copy is left behind. `discordBotRequest` is the raw bot REST call for everything that is not a channel message; the transport retries a 429 once when the wait is ≤5s. `/api/settings/discord-route/check` reads every configured channel as the bot, so a leader can confirm access before trusting the new routing (it proves visibility, not Send Messages). **Interactions** (`discord/interactions/`): `POST /api/discord/interactions` is the Developer Portal's Interactions Endpoint URL, authenticated by Discord's **Ed25519 signature** (`verify.ts`, over the raw body, with a 5-minute replay window) rather than the session cookie. `actor.ts` is the bot's `authorizeActive`: Discord user id → `persons.discord_user_id` (matched in the free-text forms `normalizeDiscordId` accepts) → the person's **live** `access_role`; Discord roles are never consulted, and two persons claiming one Discord id resolve to nobody. `router.ts` (dependency-injected, tested without a DB) turns a handler's `HandlerResult` — `reply` / `defer` / `update` / `choices` — into Discord's response; a `defer` acknowledges inside Discord's 3-second window and its work runs in `after()`, editing the reply in via `editInteractionReply` (interaction-token auth, never re-routed by the override). Handlers live in `commands/` and register in `interactions/index.ts`; component custom ids are versioned `ns:vN:args` (`customId.ts`) because a button outlives the code that wrote it. Definitions are pure (`commands/definitions.ts`) and pushed by `POST /api/discord/commands` (Settings → Sync slash commands; guild-scoped with `DISCORD_GUILD_ID`). Commands so far: `/me` (any linked member), `/whois` and `/link` (dashboard access; autocomplete gated too) — both render `members/profilePost.ts`, a per-account profile whose `leadership` audience adds kick-list and access details. **Alert actions** (component handlers, all gated on dashboard access): a queued hit-up suggestion is now posted to the leadership channel (`strikes/reviewPost.ts` + `reviewAlert.ts`, fired from `scan.ts` with only the rows that scan inserted) with Confirm / Dismiss, which run `strikes/review.ts` — the same code `/api/rules/review/[id]` now calls, with a conditional pending→reviewed claim so two leaders racing produce one winner, and a failed strike write handing the suggestion back to pending; the kick alert has Handled and Welcome back (asks privately first, since removing the entry deletes its reason, then stamps the alert via the bot); the unlinked-join alert has a select that opens a private **link panel** (`unlinked/linkPanel.ts`): one-click "Alt of …" buttons for the likely owners (`unlinked/match.ts`, pure — alts are usually named like their owner, so names are folded for case, decoration and alt-style suffixes, with a shared clan breaking ties), Discord's member picker (the owner's Discord resolves to their person), and "New person: <in-game name>"; once linked, a person without a Discord is offered the picker for theirs. `/link account [person]` (both autocompleted, person matched by its name or any of its accounts) covers an owner who is neither suggested nor on Discord. All of it goes through `unlinked/link.ts`, which — unlike the dashboard route — refuses an account linked since the alert was posted, refuses a Discord id another person already holds (two persons on one id lock that user out of the bot), and never replaces a person's different Discord. Every action stamps the alert in place with who acted (`interactions/resolution.ts`: an "Actions" embed field, used-up buttons removed, recoloured once nothing is left open), and a stale button (already reviewed from the dashboard) stamps the current state rather than acting again. `deferUpdate` acknowledges a click and edits the message afterwards; if that work fails, the message is left alone and the clicker gets an ephemeral follow-up. Posts warning/strike embeds to the per-clan channel (falling back to `DISCORD_DEFAULT_CHANNEL_ID`), optionally @-mentioning the member via their linked `discord_user_id`. Every send is fail-safe: a missing channel is a silent no-op and a non-2xx is swallowed, so a Discord failure never fails the strike write. A family-wide **routing override** (migration 027) redirects *every* notification to one channel while `discord_override_enabled` is on — the testing-phase mode. It is applied inside `sendDiscordMessage`, the single choke point every message passes through, so no caller can bypass it; mentions stay live and each message is labelled `ClanOps · test routing`. Routing has a second axis, the channel's **purpose** (migration 029): `destinationForClan(clanId, purpose)` resolves an `'announcement'` to the family-wide `discord_announcement_channel_id` setting, and everything else — strikes, warnings, transfer calls, lineup notices — to the clan channel the addressed people already read. The chain **falls through** rather than branching, so a blank announcement setting means announcements keep landing in the clan channel exactly as before the axis existed; only the CWL clan rosters route as announcements (the leadership digest deliberately does not — it reports shortfalls, which is leadership's read, not a family publication). A third purpose, `'leadership'` (migration 035, `discord_leadership_channel_id`), carries leadership-only alerts — currently the kick-list arrival alert, which names the kick reason — under the same blank-inherits fall-through. A fourth, `'unlinked'` (migration 036, `discord_unlinked_channel_id`), carries the **unlinked-join alert** (`lib/unlinked/`: pure `joinPost.ts` + `joinAlert.ts`, a fail-safe `runFullSync` step after the kick watch): every arrival with no `person_id` is posted per clan with the Leadership role pinged in plain content. Kick-listed accounts are skipped (the kick alert covers them), as is a clan's first sync (`syncClan` returns `firstSync`), which would otherwise ping a whole newly added roster. Each alert is recorded per joiner in `unlinked_join_alerts` (migration 040: message id + the channel the bot *actually* posted to, override included), and every later sync **settles** open ones first (`settleUnlinkedJoinAlerts`): a joiner who has since left, moved to another family clan, been linked outside the alert or been removed is stamped onto the alert and dropped from its select (pure `joinOutcome` / `settleAlert`), recolouring it resolved once nobody is left — stamped rather than deleted, since the ping already went out and a message that vanishes leaves leadership with a notification to nothing. A link made from the alert's own panel is not stamped twice (it is no longer offered in the select); a row closes only once the edit lands, so a Discord failure retries next sync, within a 30-day window. Blank, it inherits the leadership channel before the clan channel. A clan's own `clans.discord_join_channel_id` (migration 039, set on the Clans tab) wins over all of these — a channel **or a thread**, since the bot posts into a thread by id exactly as into a channel — so each clan's joiners can be triaged apart (e.g. one thread per clan under a #new-joins channel). Kick alerts deliberately do not follow it: they name the kick reason and stay in the leadership channel. The routing rows are kept out of the generic settings blob: `/api/views/settings` leaves them (`ROUTE_SETTING_KEYS`) out of the settings it serves, and `/api/settings/discord-route` (gated on `leader.manage`) serves them and validates each channel id on write; the settings read is cached with the override behind one 15s-TTL query, so the purpose axis costs no extra round trip per message. `renderRoundLineup` is the CWL round-reveal notice — swapped-in accounts get a real @mention, swapped-out are named with `allowed_mentions.users` restricted so they cannot be pinged. Two send primitives: `sendDiscordMessage` for one-shot announcements and `postOrEditDiscordMessage` for a **living** message edited in place (used by the CWL roster posts) — the latter falls back to posting fresh when an edit fails, which is what self-heals a stored id after the destination moves (a re-pointed clan channel, or the routing override being flipped).
- **`members/thRoles.ts` / `thRoleSync.ts`** — automatic **town-hall roles** on the family Discord. Every person with a linked `discord_user_id` gets one `TH<n>` role per level among their **active** accounts (a TH17 main + TH12 alt hold both), TH9 and up only. The role set is derived, not configured: TH9 to the highest active level, so a new town hall release creates its own role the first time an account reaches it. Roles are remembered by **id** in `discord_th_roles` (migration 041) so a leader renaming one changes nothing; a hand-made role with the matching name is adopted rather than duplicated, and only these roles are ever added or removed — stale ones (upgraded, left the family, unlinked) are stripped. A fail-safe last step of the full `runFullSync`, gated to one **finished** pass a day by `discord_th_role_sync` (which also holds a claim so overlapping syncs cannot both create a role); a pass that hits its 25s budget leaves the day open and the next sync resumes. Needs `DISCORD_GUILD_ID`; listing members needs the **Server Members** privileged intent, without which it falls back to per-person lookups (and cannot clean roles off members the registry no longer links). Refuses to act on an empty account read, which would otherwise strip every role.
- **`permissions.ts` / `permissions-server.ts`** — see Auth above. **`ClanContext.tsx` / `useCurrentUser.ts`** are the two client-side data hooks (selected-clan context; live `/api/auth/me` user + capabilities).

### API & sync
Routes live under `src/app/api/**/route.ts`. `POST /api/sync` (optional `clanId`, else all active clans) is the workhorse: it reconciles rosters, ingests regular + CWL wars, runs rule detectors, and best-effort refreshes CWL live state (CWL failures are swallowed so they never fail the roster sync). Only one pass runs at a time: `runFullSync` claims the single-row `sync_lease` (migration 044) and a second caller returns `skipped` (a lease older than 2 minutes belongs to a killed pass and is taken over; with no row it runs unguarded). After the rosters, the post-roster steps run in stages — transfers + both arrival alerts together, then CWL + regular wars together, then the rule scan — and the TH-role step is capped by the pass's overall 50s deadline. CoC and Discord fetches time out after 10s, and CoC reads are `cache: 'no-store'` (a cached war read would push back every attack's `first_seen_at`). The CWL poll skips rounds already stored as `warEnded` and fetches only the clan's own war in a round it already knows (`cwl/api.ts`). Sync is triggered by authenticated dashboard requests **and** by `POST /api/cron/sync` — a machine-auth endpoint for external schedulers that authenticates via a `Bearer $CRON_SECRET` header (constant-time compare, disabled when the env var is unset) rather than the JWT cookie. Notable lifecycle routes: `DELETE /api/persons/[id]` (removes a person, detaching accounts back to Unlinked; requires `leader.manage` and rejects a person who still holds access), and account link/unlink via `/api/members/link` (auth-enforced through `authorizeActive`).

### Database migrations
Base schema is `supabase_setup.sql`. Incremental changes are numbered SQL files in `supabase/migrations/` (e.g. `010_cwl_schema.sql`). On merge to `main`, `.github/workflows/db-migrate.yml` runs `supabase db push` to apply any not-yet-recorded migrations to the **production** project — do **not** hand-run prod SQL anymore (that drift is what this replaces). Add one with `supabase migration new <name>`; see `supabase/README.md` for the flow and the one-time baseline of `001`–`012` (the series continues past `022_role_capabilities`). **API roles are locked out** (migration 042): `anon`/`authenticated` hold no privileges and every table has RLS with no policies, so only the secret key reaches data. A new table must `ENABLE ROW LEVEL SECURITY` and grant to `service_role` only — never to `anon` (copying the `GRANT … TO anon` line from 035/040/041 would reopen it). For the **testing** project, run `npm run db:grant` if the secret key hits "permission denied" after adding a table.

### Environment
`.env.local` (dev/prod) and `.env.testing` hold: `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (required — the server-only secret key every route uses; the anon key has had no database access since migration 042), `JWT_SECRET` (required; signs sessions and keys login-code hashes), `COC_API_TOKEN`, optional `COC_API_PROXY_URL` (recommended — the CoC API requires IP allowlisting, so a fixed-IP proxy is used), optional `CRON_SECRET` (bearer token for `/api/cron/sync`), `DISCORD_BOT_TOKEN` (required for login, which DMs the code; without it nothing is posted either), `DISCORD_DEFAULT_CHANNEL_ID` (the family-wide fallback channel), `DISCORD_APPLICATION_ID` + `DISCORD_PUBLIC_KEY` (slash commands; the interactions endpoint rejects everything without the key) and optional `DISCORD_GUILD_ID` (register commands to the family server only; also required for the TH roles), and optional `RULES_FRESH_START` (an ISO date; the war-rule detectors never scan or strike any war that ended before it — set it to the reset moment when starting a clean strike system so previously-ended wars stay invisible even after their strikes are wiped).
